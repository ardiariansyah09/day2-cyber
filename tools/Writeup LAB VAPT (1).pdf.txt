mengeksploitasi celah.

3. IDOR - Broken Access Control
IDOR (Insecure Direct Object Reference) terjadi ketika aplikasi gagal memvalidasi apakah
pengguna yang meminta suatu data adalah pemilik sah dari data tersebut.
Kita menggunakan Burp Suite Repeater. Header Authorization (token login ) tetap sama, namun
dengan mengubah ID di URL (misal: /rest/basket/1, /rest/basket/2, /rest/basket/6), server "secara
buta" mengembalikan data keranjang milik pengguna lain.
Menunjukkan bukti baseline untuk dua user berbeda sehingga nantinya kita bisa membandingkan
hasil saat melakukan serangan IDOR (mengubah parameter ID resource) pada Burp Repeater
untuk mengakses data milik user lain (admin) saat login sebagai user biasa.

Dampaknya pelanggaran privasi pengguna. Penyerang dapat mengumpulkan data intelijen

IDOR (Insecure Direct Object Reference / broken access control) terjadi ketika aplikasi
mengekspos identifier (ID) internal — mis. cartId, orderId, atau userId — dan tidak melakukan
pengecekan akses (access control) yang memadai sebelum mengembalikan data. Skenario
latihan: endpoint yang mengambil isi keranjang menerima parameter ID; attacker (yang login
sebagai anna12) mengubah ID di request (mis. via Burp Repeater) menjadi ID keranjang admin.
Jika server mengembalikan isi keranjang admin tanpa memverifikasi bahwa peminta memang
pemiliknya atau memiliki hak akses, maka itu adalah IDOR.
Pemetaan GRC:
● Severity: HIGH (7.5)
● CWE: CWE-639: Authorization Bypass Through User-Controlled Key
● ISO 27001:2022: A.5.15 (Access control), A.8.3 (Information access restriction)
● NIST SP 800–53: AC-3 (Access Enforcement), AC-6 (Least Privilege)

4. Cross-Site Scripting (XSS)
XSS pada search bar membuktikan bagaimana satu titik input yang lemah bisa dieksploitasi
dengan berbagai cara, dari sekadar pop-up hingga pengambilalihan akun.
Fitur pencarian gagal melakukan sanitasi input, yang memungkinkan tiga jenis serangan:
● Reflected XSS: Payload <img src=x onerror=alert('xss')> dieksekusi, membuktikan script
arbitrer bisa berjalan.
● HTML Injection: Payload <a href="...situs-phishing.com">Klik di sini!</a> berhasil
me-render link palsu di halaman hasil pencarian, sebuah PoC sempurna untuk phishing.
● CSTI 	(Client-Side 	Template 	Injection): 	Payload 	AngularJS
{{constructor.constructor('alert(1)')()}} berhasil dieksekusi, membuktikan adanya celah
yang lebih dalam di level framework.
Server “memantulkan” apa pun di parameter q= (pencarian) langsung ke halaman. Ini
memungkinkan injeksi tag HTML (<img>, <a>) dan juga sintaks template AngularJS ({{...}}).
a. Temuan: Reflected XSS (Payload Sederhana)
Ini adalah pembuktian awal bahwa celahnya ada.

Ini adalah PoC XSS paling klasik. Kita menyuntikkan payload <img src=x onerror=alert('xss')>.
Karena server tidak memfilter input kamu, dia "memantulkan" HTML itu kembali ke browser.
Browser mencoba memuat gambar src=x (yang tidak ada), ini memicu onerror, dan script

Ini adalah variasi payload XSS dengan menambahkan atribut style="display:none" untuk

XSS. Hal ini menunjukkan bahwa input masih dapat dieksploitasi melalui HTML injection dan

b. Reflected XSS (Dampak Nyata: Pencurian Cookie!)
Ini adalah “bom”-nya. Jauh lebih bahaya dari alert('xss')
Pengujian menunjukkan bahwa payload XSS berhasil membaca informasi cookie melalui
document.cookie. Hasilnya memperlihatkan bahwa beberapa cookie, termasuk JWT yang
memuat informasi autentikasi dan identitas pengguna, dapat diakses oleh JavaScript. Kondisi ini
berpotensi menyebabkan pencurian token autentikasi dan meningkatkan risiko Session Hijacking
maupun Account Takeover apabila token tersebut masih valid dan dapat digunakan oleh pihak
tidak berwenang.
c. HTML Injection (Skenario Phishing)
Ini adalah temuan terkait, di mana kita tidak menyuntikkan script, tapi menyuntikkan HTML
biasa untuk menipu pengguna.
